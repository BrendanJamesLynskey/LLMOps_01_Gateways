01

What a Gateway Does & Why

An LLM API gateway sits between your application code and every upstream model provider. It is the single seam where cross-cutting concerns — authentication, rate-limiting, cost attribution, observability, failover — can be enforced without touching application code.

Without a gateway

  • Each service holds its own API keys
  • Provider URLs hard-coded — changing vendor = code change
  • No centralised cost tracking or spend caps
  • Retry / fallback logic duplicated in N services
  • No uniform audit log across providers

With a gateway

  • One API key per team; gateway holds real provider creds
  • Switch provider by editing gateway config, zero downtime
  • Per-customer spend attribution at one chokepoint
  • Retry, backoff, fallover in the gateway, once
  • Uniform OpenTelemetry span per request, every provider

The five gateway obligations

ObligationImplementation
Protocol normalisationMap every provider to a single OpenAI-compatible API surface (POST /v1/chat/completions)
Credential isolationClients authenticate to the gateway; gateway holds provider keys in a secrets store
Traffic policyRate limits (token bucket), per-tenant quotas, spend caps enforced before the upstream call
ResilienceTimeout, retry with exponential backoff, provider failover without client awareness
ObservabilityStructured log + trace per request: model, token counts, latency, cost estimate, status
Cost context

Without a gateway, a 429 from OpenAI surfaces as a raw HTTP error to your user. With a gateway, that 429 triggers an automatic fallback to Anthropic or a queued retry — the user sees nothing. That single behaviour justifies most gateway deployments on its own.

02

LiteLLM — OpenAI-Compat Shim, Models, Fallback

LiteLLM (pip install litellm, MIT licence, v1.x as of 2025) translates between 100+ provider APIs and the OpenAI request/response schema. It can run as a Python library, as a proxy server (litellm --port 4000), or embedded in another gateway.

litellm proxy — config.yaml
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY

  - model_name: gpt-4o           # same alias — fallback
    litellm_params:
      model: anthropic/claude-3-5-sonnet-20241022
      api_key: os.environ/ANTHROPIC_API_KEY

router_settings:
  routing_strategy: latency-based-routing
  num_retries: 3
  timeout: 30
  allowed_fails: 2
  cooldown_time: 60        # seconds before retrying a failed model

general_settings:
  master_key: sk-my-internal-key
  database_url: os.environ/DATABASE_URL  # Postgres for spend tracking

Routing strategies

  • simple-shuffle — random across healthy deployments
  • least-busy — fewest in-flight requests
  • latency-based-routing — EWMA of p50 latency
  • cost-based-routing — cheapest per token
  • usage-based-routing — TPM / RPM headroom

Virtual keys & spend

Issue per-team virtual keys (sk-…). Each key carries a max_budget and budget_duration. The Postgres spend table is updated after every response. Budget exhaustion returns HTTP 429.

Callbacks

Pluggable callbacks on success/failure: langfuse, helicone, s3, datadog, prometheus. Set once in config, fires for every request regardless of provider.

Streaming note

LiteLLM normalises SSE streaming: every provider’s chunk format is converted to OpenAI data: {"choices":[{"delta":{"content":"…"}}]}. The last chunk always carries usage so token counts are available even in streaming mode.

03

Portkey — Caching, Guardrails, Routing

Portkey (portkey-ai SDK, hosted at api.portkey.ai or self-hosted via Docker) adds a managed control-plane layer. It extends the OpenAI SDK by replacing the base_url and injecting a per-request Config object via the x-portkey-config header.

Python — Portkey client initialisation (SDK v1.x)
from portkey_ai import Portkey

client = Portkey(
    api_key="pk-my-key",
    virtual_key="openai-vk-xxxxx",
    config={
        "cache": {"mode": "semantic", "max_age": 3600},
        "retry": {"attempts": 3, "on_status_codes": [429, 500, 503]},
        "strategy": {
            "mode": "fallback",
            "on_status_codes": [429, 500]
        },
        "targets": [
            {"virtual_key": "openai-vk-xxxxx", "weight": 0.7},
            {"virtual_key": "anthropic-vk-yyy", "weight": 0.3}
        ]
    }
)

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Summarise the Kyoto Protocol."}]
)

Key Portkey capabilities

Semantic cache

Embeds the prompt; cosine-similarity threshold (default 0.97) determines a hit. Cache entries stored in Portkey’s Redis-backed store (or self-hosted Redis via PORTKEY_REDIS_URL). TTL configurable per-request via x-portkey-cache-max-age.

Guardrails

Before/after hooks: prompt_injection_detection, pii_redaction (regex + model-based), content_moderation (OpenAI mod API or custom). Hook result is allow, block, or transform. Each hook emits a scored annotation in the trace.

Load balancing modes

loadbalance (weighted round-robin), fallback (primary → secondary on error), conditional (route on metadata field, e.g. user_tier == "enterprise").

Observability

Every request logs to Portkey Logs (hosted) or any OTel-compatible collector. Spans carry portkey.prompt_tokens, portkey.completion_tokens, portkey.cost, and portkey.cache_status attributes.

OpenRouter — Pay-as-You-Go Aggregator

OpenRouter (openrouter.ai) exposes 200+ models from 40+ providers behind a single OpenAI-compatible endpoint at https://openrouter.ai/api/v1. You pay in OpenRouter credits; OpenRouter handles per-provider billing, rate limits, and failover.

curl — routing via OpenRouter model string
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "HTTP-Referer: https://myapp.example.com"  # required for attribution \
  -H "X-Title: My App" \
  -d '{
    "model": "anthropic/claude-3-5-sonnet",
    "messages": [{"role":"user","content":"Hello"}],
    "route": "fallback",
    "models": [
      "anthropic/claude-3-5-sonnet",
      "openai/gpt-4o",
      "google/gemini-1.5-pro"
    ]
  }'

Provider routing semantics

Route valueBehaviourUse case
fallbackTry models in order; next on 4xx/5xxMaximum uptime
load_balanceDistribute by cost × latency scoreCost/latency trade-off
(omitted)Single model, OpenRouter picks cheapest providerSimple lowest-cost

Response headers for observability

HeaderContent
X-OR-ModelActual model used (may differ from requested due to fallback)
X-OR-ProviderProvider that served the request
openrouter-generation-idUUID; fetch full usage & cost from GET /api/v1/generation?id=…
Vendor lock-in trade-off

OpenRouter reduces provider lock-in at the cost of introducing OpenRouter as a dependency. For production workloads consider whether a self-hosted LiteLLM proxy gives you equivalent routing with fewer third-party dependencies. OpenRouter is excellent for prototyping and teams that don’t want to manage provider relationships.

Custom Gateway Patterns

When LiteLLM, Portkey, and OpenRouter don’t cover your requirements — bespoke auth, organisation-specific PII rules, proprietary models, complex routing logic — you build a thin gateway layer on top of a reverse proxy or as a standalone service.

Common patterns

Reverse-proxy overlay (Nginx / Envoy / Traefik)

An Nginx lua_block or Envoy ext_proc filter intercepts the request at the proxy layer: validates the JWT, enriches the request with X-LLM-Budget-Remaining and X-LLM-Tenant headers, then forwards to the upstream API. No separate process; works at wire speed for auth checks.

FastAPI middleware gateway

A FastAPI app with @app.middleware("http") that holds provider creds in Vault. Implements POST /v1/chat/completions, rewriting the model field and injecting system-prompt metadata. Small enough to own fully; easy to extend. Latency overhead ≈ 2–5 ms.

Request / response hooks pattern

Define a hook chain: pre_request[] → upstream → post_response[]. Each hook is an async coroutine. Hooks can mutate the request/response or abort with a status code. Inspired by LangChain callbacks but at the HTTP layer.

Model-alias registry

Maintain a YAML or Postgres-backed registry mapping logical names (summariser-v2) to versioned model IDs and provider endpoints. The gateway resolves aliases at request time. Roll back a model by updating one registry row, with zero application changes.

FastAPI custom gateway — minimal skeleton
from fastapi import FastAPI, Request, HTTPException
import httpx, os

app = FastAPI()
REGISTRY = {"summariser-v2": ("openai/gpt-4o", "https://api.openai.com/v1")}

@app.post("/v1/chat/completions")
async def chat(req: Request):
    body = await req.json()
    alias = body.get("model", "summariser-v2")
    model_id, base_url = REGISTRY.get(alias, (alias, "https://api.openai.com/v1"))
    body["model"] = model_id
    async with httpx.AsyncClient(base_url=base_url) as c:
        r = await c.post("/chat/completions", json=body,
                         headers={"Authorization": f"Bearer {os.environ['PROVIDER_KEY']}"},
                         timeout=60)
    return r.json()

Multi-Provider Failover Strategies

A failover strategy is more than “try B if A fails”. Production LLM traffic has four distinct failure modes, each needing a different response.

Failure modeHTTP statusStrategy
Rate limit exhausted429Wait for Retry-After header (seconds), or immediately route to secondary — 429 means “not now”, not “broken”
Provider outage500, 502, 503Failover to secondary; mark primary as unhealthy for a cooldown window (60–300 s)
Context-window overflow400 (context_length_exceeded)Fallback to a model with larger context, not a random secondary
Slow response / timeout(no response)Client-side deadline; hedge request to secondary after p95 latency + 20% with cancellation on first response

Hedged requests

A hedged request fires a second request to a different provider after a deadline, cancels the slower one on first response. Effective against tail latency without the cost of always calling two providers. LiteLLM supports this via routing_strategy: latency-based-routing with num_retries; implement manually with asyncio.wait(..., return_when=FIRST_COMPLETED).

Circuit breaker — don’t skip it

Track provider error rates in a sliding window (e.g. 10 requests, 5-second bucket). Open the circuit when error rate > 50%; half-open after cooldown; close on success. LiteLLM’s allowed_fails + cooldown_time implements this. Without a circuit breaker, a flapping provider generates cascading retries that amplify your own latency.

PII Scrubbing at the Boundary

The gateway is the last point before data leaves your network. Scrubbing PII here means no client change is required and the redaction applies uniformly across every model and every team.

Detection approaches

Regex patterns

Fast, low-latency (< 1 ms). Covers well-structured PII: UK NI numbers ([A-Z]{2}[0-9]{6}[A-D]), NHS numbers, credit card PANs (Luhn check), email, IPv4/IPv6, UK postcodes. False-negative rate high for free-text names.

NER models (spaCy / Presidio)

Microsoft Presidio v2 runs a spaCy en_core_web_lg NER pass. Detects PERSON, ORG, LOC, DATE, PHONE, CREDIT_CARD. ~5–20 ms per request at CPU. pip install presidio-analyzer presidio-anonymizer. Redact with placeholder tokens (<PERSON_1>) for reversibility.

LLM-based detection

Small classifier model (e.g. BERT fine-tuned on PII) or a fast frontier model used as a pre-filter. Highest recall; adds 50–200 ms. Use only for async pipelines or when compliance demands high recall. Not suitable for <100 ms latency SLOs.

Presidio redaction in a gateway hook (Python)
from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

analyzer  = AnalyzerEngine()
anonymizer = AnonymizerEngine()

def scrub_messages(messages: list[dict]) -> list[dict]:
    for msg in messages:
        text = msg.get("content", "")
        results = analyzer.analyze(
            text=text, language="en",
            entities=["PERSON", "EMAIL_ADDRESS", "CREDIT_CARD",
                       "UK_NHS", "PHONE_NUMBER", "IBAN_CODE"]
        )
        msg["content"] = anonymizer.anonymize(text, results).text
    return messages
Reversibility and audit

Replace PII with deterministic placeholder tokens rather than random UUIDs so you can correlate gateway logs back to source records if needed. Store the mapping in an encrypted side-channel keyed on request ID. Never log the original PII — only log the placeholder and the entity type (PERSON_1, EMAIL_1). UK GDPR Article 25 requires “data protection by design”; scrubbing at the gateway satisfies that obligation without re-architecting every consuming service.

What to Take Away

  • A gateway is mandatory at scale. Without one you have M×N credential, retry, and observability problems. With one you have M+N.
  • LiteLLM proxy is the lowest-friction self-hosted option: pip install litellm, one YAML, 100+ providers. Use latency-based-routing or cost-based-routing as your default strategy.
  • Portkey layers on guardrails, semantic cache, and conditional routing with a hosted control plane — useful when you want that without building it yourself.
  • OpenRouter externalises multi-provider billing and failover entirely; pay the convenience premium or self-host for cost control.
  • Failover needs four separate paths: rate-limit (pause/reroute), outage (circuit-break), context overflow (capability fallback), timeout (hedge).
  • Scrub PII at the gateway with Presidio + regex; <20 ms overhead for CPU-only; satisfies GDPR Article 25 without touching application code.
  • Pick your shape: sidecar for blast-radius isolation, central for audit simplicity, edge for client-facing global products.
